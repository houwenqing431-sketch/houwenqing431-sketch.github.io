实验2 数据看板的设计与实现

用 Streamlit + Pandas + Plotly 从零做一套电商销售数据看板：自己造数据、自己定颜色规则、自己写图表，最后再自己想办法证明”它真的能跑”。
这篇记录里最值得看的可能不是成品，而是我踩过的那些坑——尤其是几条”看起来对、其实在骗人”的图表。

一、先想清楚它要回答什么问题

实验要求分四大模块：数据概览、维度统计、趋势分析、明细数据。但我不想为了凑模块而凑模块，所以先问自己：运营的人早上打开这块屏，是为了回答哪几个问题？

他想知道 对应模块 关键指标
生意整体好不好？ 数据概览 销售额、订单量、客单价、目标达成率、毛利率、退货率
好在哪里、差在哪里？ 维度统计 品类结构、渠道结构、地区结构
在变好还是变差？ 趋势分析 日销售额、7 日均线、上期同段对比、大促脉冲
具体是哪几个品？ 明细数据 品类/渠道/地区汇总、商品 Top N、订单明细

版面按”总览 → 拆解 → 走势 → 明细”自上而下递进，所有筛选器集中在最上面一行——一次筛选，全页同步，而不是每张图各自带一套筛选器。

二、配色这次我没凭感觉挑

以前做可视化，颜色都是”看着顺眼就行”。这次了解到一套挺硬的规范，就按它来做了，几条规则值得记下来：

1. 分类色板是 8 个固定色位、固定顺序，第 9 个序列不许生成新颜色。
超过 8 个就该归并成”其他”或者拆成小多图，而不是硬凑一个肉眼分不出来的第 9 色。

2. 颜色跟着”实体”走，不跟着排名走。
京东永远是 1 号色位、天猫永远是 2 号。这样筛选之后颜色不会重新分配——读者记住的”天猫是蓝色”不会被推翻。

3. 名义分类的条形图，所有条用同一个颜色。
这一条我一开始不理解：给每个品类不同颜色不是更好看吗？后来想明白了——条形图的长短已经表达了大小，再用颜色深浅编码一遍，等于把唯一的”身份通道”浪费在重复信息上。所以品类销售额那张图 7 根条全是主色，需要突出时用”强调一个、其余置灰”。

4. 量值编码（热力图）只用单色阶，同色相由浅到深，绝不用彩虹色。

5. 状态色语义专用。 正常/关注/超限这三个颜色不参与分类取色，而且永远配图标 + 文字——颜色永远不是唯一线索，色觉障碍用户也能读。

6. 绝不使用双 Y 轴。 销售额和订单量量纲不同，就老老实实拆成上下两张图。这是最容易被忽略、也最容易骗人的一处。

配色定下来之后我还写了个小脚本把深浅两套色板分别跑了一遍色觉障碍可分辨度和对比度校验——深浅两套是各自独立取值的，不是把浅色简单反相。校验发现浅色模式下青绿/黄/品红三个色位对比度低于 3:1，规范要求这种情况必须补上”直接标注 + 表格视图”作为兜底，于是环形图的大扇区都标了百分比，明细区也全都有对应的数据表。

三、数据：先造一份”像真的”，再故意弄脏它

实验说数据可以 AI 生成。但纯随机数堆出来的流水很无聊——折线图是一条毛刺，看不出任何故事。所以我是先建业务规律，再生成数据：

  • 长期增长：180 天约 +60% 的上升趋势
  • 周末效应：周六日流量 ×1.15
  • 大促脉冲：618 / 双 11 / 双 12 / 88 会员节 ×1.9~2.8，每月 8/18/28 日会员日 ×1.3
  • 结构差异：数码家电偏京东、美妆服饰偏抖音直播、食品生鲜偏拼多多（一张”品类 × 渠道偏好矩阵”）
  • 渠道退货率差异：直播带货 12.5%，自营商城 3.0%
  • 下单双高峰：上午 10-11 点、晚间 20-22 点

这样出来的趋势图才有大促尖峰、渠道占比图才有结构性差异、预警模块才有真实素材。

然后故意把它弄脏

真实业务里的数据不会是干净的，所以我注入了 6 类最常见的脏数据：

脏数据类型 注入方式 注入量
重复订单 整行复制，订单号完全重复 500
关键字段缺失 数量/单价/地区/渠道/评分置空 1,045
非法数量 0 与负数 164
极端值 单价被误乘 40 倍 61
格式不规范 品类名带半角/全角空格、别名 738
文本混入数值列 单价 = “暂无报价” 82

其中全角空格这一项是故意加的："数码家电" 和 "数码家电　"（U+3000）在屏幕上看起来一模一样，但分组统计时会变成两个品类。清洗时得先正则统一清理：

清洗流程一共 7 步，每一步都记录影响行数，最后落到 data/预处理报告.md：

原始 20,500 行 → 干净 19,088 行，保留率 93.1%，并通过 9 项质量断言（关键字段无空值、订单号唯一、金额勾稽一致、评分在 1~5……）。断言不过就直接中断落盘，不让脏数据流进看板。

有一个细节我觉得挺有意思：按品类分组用 IQR 剔极端值，实际剔掉了 240 条，但我注入的只有 61 条。核对之后确认多出来的是真实的长尾贵价商品（笔记本、跑步机这类），属于正常分布的边缘。所以这里用的是 3 倍 IQR 而不是教科书的 1.5 倍——为了让”异常值处理”不误伤真实业务，并且在报告里如实记录剔除量。

四、图表：几个我特意”不这么做”的地方

不做双 Y 轴，拆成两张图

销售额和订单量放一张图、两个 Y 轴，看起来紧凑，实际上很危险：两个刻度的对齐方式是任意的，图会凭空造出一个数据里不存在的相关性。所以趋势区是上下两张图，并在图上注明”避免双 Y 轴造成的误读”。

环形图顺时针，并且不超过 6 段

Plotly 的饼图默认是逆时针画的，而图例是从上往下排的——两者顺序正好相反，读者对着图例会一直对错。得显式指定：

顺带一提，扇区之间用的是背景色 2px 缝隙，不是描边——描边会多出一圈”不是数据”的墨水。

雷达图有两个坑

坑一：序列数上限。 雷达图属于”任意两个标记都可能相邻”的形式，颜色两两之间都要能分辨。我用的这套色板在”任意配对”这个更严的测试下，只有前 3 个色位能全部通过——所以雷达图最多同时对比 3 个品类。

坑二：归一化的基准。 一开始我是按”被选中的那几个品类”做 min-max 归一化的，结果每换一组对比对象，同一个品类的形状就变了；而且被选中的三项里必然有一项是 0 分，图形退化成一根刺。改成以”当前窗口内的全部品类”为基准，并把值域映射到 10~100（最低者不塌到圆心），图形才真正可比：

热力图：长尾数据得封顶

地区 × 品类销售额是典型的长尾分布——“华东 × 数码家电”一格把量程拉满，其余全挤在色阶最浅的一头，整张图几乎一个颜色。解决办法是把色阶上端截到 88 分位：

极端格显示为饱和色，色阶图例上注明”≥13 饱和”。截断只影响颜色——悬浮提示和表格视图里仍然是真实值，信息没有丢。

同一张图里右边那个”星期 × 时段”热力图还藏着一个更隐蔽的坑：各时段箱覆盖的小时数不一样（上午 6 小时、午间只有 2 小时），直接画总量等于拿 2 小时对比 6 小时。结果就是”上午”亮得离谱，和另一张按小时统计的时段分布图完全矛盾。改成统一换算成”每小时平均订单量”之后，两张图的结论才一致。

六、踩坑记录

这部分是这篇最想留下来的东西。

1. pandas 3.0 下时间戳加 Timedelta 报 UFuncBinaryResolutionError。
dates.values 在 pandas 3.0 是 datetime64[us]，而 pd.Timedelta 对象数组是 object，两者不能直接相加。得把偏移量构造成同精度的 timedelta64 再运算：

2. Streamlit 会偷偷覆盖我调好的图表配色。
st.plotly_chart 默认套 Streamlit 自己的主题，把我设置的字体、颜色、边距全盖掉。必须显式关掉：theme=None。这个坑很阴——图上不是报错，只是”看起来不太对”。

3. 数据卡片的数字滚动动画算不出来。
用 CSS 计数器做滚动效果，但千分位逗号会让计数器解析失败（int("1,234") 直接报错）。最后让卡片数字单独走一套不带逗号的格式化逻辑，反正统一按”万/亿”换算后数字本身就很短。

4. 长图截图里侧边栏错位。
我用 headless Chrome 截了一张 1680×8600 的整页长图，结果侧边栏内容被裁在左边缘。查了半天 DOM 才发现布局是好的——是超高视口下 Chrome 的分屏合成不可靠。而且 8600px 的长图缩放后本来也看不清。改成”一屏一张”的滚动截屏就都解决了。

5. 改完公共模块，看板刷新了但样式没变。
Streamlit 的热重载会重跑主脚本，但已经 import 的模块还留在 sys.modules 里。改完 src/ 下的公共模块得重启服务。后面我所有的截图和自检都在重启后重跑。

6. 切到亮色主题，图表变亮了但控件还是暗的。
Streamlit 的主题是编译期注入的，运行时没有官方切换接口；而且 1.65 并没有把主题令牌暴露成 CSS 变量可以直接覆盖。只能逐个 data-testid 覆盖控件外壳，并把覆盖全部写成引用自定义主题变量（var(--surface-2) 这类），这样同一套规则在深浅两色下都成立。

七、怎么证明”它真的能跑”

这部分我觉得是整次实验收获最大的。

改完代码总要验证，但看板类项目有个麻烦：它的产物是浏览器里的画面。靠人肉点一遍不现实，而我也没有可以目视的图形界面环境。

第一层：无浏览器自检

Streamlit 官方提供了 AppTest，可以在无浏览器环境下把 app 完整跑一遍，并直接捕获里面的 Python 异常：

我把默认路径和几条容易漏测的交互分支（钻取、实时模式、亮色主题、预警触发、生成报告、极端筛选）都写成了用例，一共 13 项。它一次性抓出了三个真 bug：

  • 报告模块漏传 theme 参数，只在点”生成报告”时才炸
  • 坐标轴辅助函数不接受 nticks 参数，只在实时模式下才炸
  • 筛选到单个地区时 iloc[1] 越界——自动结论文案里写了”华东与华南合计贡献 xx%”，直接取第二行，而只剩一个地区时汇总表只有一行

第三个尤其值得说：这种 bug 手点很难碰到，但真实用户随手就能触发（”我就想看看西北区”）。

第二层：眼睛验证

自检能保证不报错，但保证不了”好不好看”。所以我用 DevTools 协议驱动本机 Chrome 截图——先等页面真的渲染完（websocket 数据回来、Plotly 画完）再按快门，不会拍到骨架屏。相比 chrome --screenshot，这一步等待是必须的。

视觉验证也确实抓到了问题：KPI 卡片因为塞了口径说明文字被撑成两行高、整排高矮不齐；”自定义”时间范围选项被挤得看不见；手机端侧边栏盖住整屏。这些都是”能跑但不好看/不好用”的问题，功能测试永远发现不了。

八、双主题与多端

亮色模式不是简单反相——两套色阶分别取值、分别校验，图表颜色也跟着切换（热力图的色阶方向在深色下要翻过来：深色背景上”浅色 = 接近 0”这个约定不成立）。

手机上做了三档响应式断点，窄屏下指标卡和进度仪表都竖排，侧边栏设为 auto 自动收起（之前写死 expanded，430px 下侧边栏会盖住整屏）。

但这里要如实说一句：这本质上是个宽屏看板，手机上四区内容拉成一长条，得滚十几屏，属于”能用但不好用”。真要移动端体验好，得另做一个精简版页面（只留指标卡 + 趋势图 + 预警），而不是靠响应式硬撑。

九、成果与不足

最终交付的东西：

  • 看板：app.py + src/ 8 个模块，四区布局 + 全局筛选 + 点击钻取 + 秒级实时 + 可调阈值预警 + 双主题
  • 数据：20,500 条含 6 类脏数据的模拟流水 → 19,088 条清洗后有效数据，附预处理报告
  • 辅助脚本：smoke_test.py（13 项自检）、export_charts.py（图表批量导出）、screenshot.py（看板截图）
  • 图表导出：12 张图表 × 深浅两套主题，可脱离看板独立阅读、直接插进报告
  • 一键报告：生成的 HTML 内含可交互图表，可以独立打开

还不足的地方：

  1. 移动端只是”能用”，没到”好用”（上面说过）
  2. 亮色模式下 Streamlit 自带控件的外壳是靠 CSS 覆盖对齐的，滚动条、日期选择弹层这类边缘元素仍会跟随配置里的暗色底——这是 Streamlit 运行时不能换主题导致的妥协
  3. 实时区目前是本地模拟生成器按加速倍率推送，不是真实数据源。不过换成 Kafka / 数据库轮询 / HTTP 接口的话，st.fragment 这套刷新机制一行都不用改
  4. 预警只做到了页面内提示，没接企业微信/钉钉机器人主动告警

小结

这次实验最超出预期的收获是：“画好一张图”和”画对一张图”是两件事。

双 Y 轴、按数值深浅给条形上色、拿 2 小时对比 6 小时——这些做法都很常见，图也都不难看，但它们会悄悄地误导读者。反过来，把配色规则、序列数上限、归一化基准这些约束想清楚之后，好看的图是规则的副产品，而不是靠审美硬调出来的。

另一收获是验证方式。以前写完代码”自己点一遍看着没问题”就算完了，这次搭起来的两层验证（AppTest 自检 + 自动化截图）抓出来的全是功能正常但体验有问题的 bug——这类问题恰恰是”点一遍”最容易漏掉的。
