Python Vibe Coding 实验一：Excel 报表 + FastAPI 记账接口

这次实验要求用 AI 编码工具完成两个任务：一个 Excel 报表生成脚本（必做），一个 FastAPI 记账接口。限制 60 分钟，可以随便用 AI 和查资料，但必须保留 AI 对话记录和代码修改轨迹。

评分表里最扎眼的一句是：“仅『让 AI 生成、跑通就交』按初级用法处理，过程分上限受限。”

所以这篇博客不打算写”我怎么让 AI 帮我写了 1000 行代码”——那部分确实很快。我想写的是另一件事：怎么确认 AI 写出来的东西是对的。

一、先别急着让 AI 写代码

我读题之后做的第一件事不是打开 Cursor，是问了三个问题，把答案写进了一张清单：

问题 结论
两道题都做吗？ 都做，共用一套工程
考题二用什么存储？ SQLite（不是内存 dict）
样例数据从哪来？ 写脚本生成含脏数据的

这三个问题看起来很小，但它们直接决定了后面代码长什么样。特别是第二个——如果选”内存 + 一把锁”，验收标准里那条「并发写入不产生数据错误」就只剩一段说辞；选 SQLite，它能变成一个跑得起来、断言得住量的测试。

我还在清单里专门写了一节「明确不做的部分」：不引入 ORM、不做前端、不做鉴权、不做 Excel 样式美化。AI 很爱顺手多加点东西，先把边界画出来比事后删代码省事。

二、考题一：清洗与报表

数据脏在哪

样例数据是我自己生成的（固定随机种子，谁跑都一样），141 行里塞了四类脏东西：

  • 8 行关键字段空值
  • 2 行日期写成 "待定" / "2026-13-45"
  • 6 行数量 ≤ 0
  • 5 行整行重复

清洗规则题目给定了三条，顺序不能乱，因为顺序会影响口径：

  1. 删除关键字段缺失的行
  2. 剔除数量 ≤ 0 的行
  3. 按全字段去重

这里有个题目没定义的点：“关键字段”是哪几个？ 我的判断是 6 个业务字段全算——因为四张输出表都要用到这 6 个字段，任一缺失这行就进不了任何统计口径。

还有一个口径问题：日期解析不出来，算”缺失”还是算新一类异常？我选择归到缺失。理由是题目只给了三条规则，硬加第四条会让清洗漏斗的计数和需求对不上。但我在漏斗里保留了一个诊断子项「其中：日期无法解析」，看得见但不多扣。

三、考题二：FastAPI 记账接口

并发这块怎么保证

验收标准说「并发写入不产生数据错误（能说明如何保证即可）」。既然只要说明就行，那我干脆做成能跑的测试。四道防线：

  1. PRAGMA journal_mode=WAL —— 读写互不阻塞
  2. PRAGMA busy_timeout=5000 —— 抢锁时等待，而不是直接抛 database is locked
  3. 写操作走 BEGIN IMMEDIATE —— 入口处就拿写锁，避免”读→写”升级锁造成死锁
  4. DB 层 CHECK 约束 —— 就算绕过应用层直接写 SQL，脏数据也进不去

验证方式是 8 线程 × 25 笔并发写，用 threading.Barrier 让所有线程尽可能同时抢锁，断言零异常、行数精确 200、金额精确 246.00。

四、AI 翻车的三个现场

这部分我觉得比”成功经验”更值得写。

翻车 1：所有接口都返回 422

写完路由第一次冒烟，全部接口 422，报错字段是 query.repo——一个本该是依赖注入的参数。

根因是 app/main.py 顶部的 from __future__ import annotations。它把所有注解变成字符串，FastAPI 求值注解时用的是模块全局命名空间，而我的依赖定义在 create_app() 闭包里，解析不到，就退化成了普通类型注解 → 被当成查询参数。

能快速定位的原因是：写完路由立刻冒烟，而不是等两个模块都写完再一起跑。

翻车 2：冒烟脚本第二次跑就挂

25 项里 8 项失败。因为脚本断言的是”空库 + 两次写入”后的精确数字，而 SQLite 是持久化的，上一轮数据还在。

翻车 3：样例数据的脏行会叠加

写生成脚本时，脏数据是从全量行里随机取的，结果一行可能既缺销售员又数量≤0。这样清洗漏斗的计数就不再是确定的，测试没法断言。

改成所有脏数据一律从「干净行」派生，保证每条脏数据只触发一条清洗规则。改完漏斗变成可预测的 141 = 10 + 6 + 5 + 120，测试直接断言。

三个 bug 都不是靠”再读一遍代码”发现的，是靠跑发现的。

五、怎么确认”它真的对”

这是整次实验里我花时间最多的部分。

问题一：74 个测试一次全绿，这件事本身可疑

测试全绿不代表测试有效——很可能有一批测试根本没断言到东西。所以我做了两件事。

第一件：写一个独立核对脚本。

它刻意不复用被测代码的任何一行：

  • 读原始表：openpyxl 直接读单元格（被测代码走的是 pandas）
  • 清洗：重新实现一遍三条规则
  • 金额：重新实现一遍 Decimal 累加
  • 再与 report.xlsx 逐项比对

23 项全部一致才返回 0。如果只用被测代码的输出做断言，代码错了一致的错，测试照样全绿。

第二件：变异测试。

六、复盘

交给 AI 的：清洗与聚合的骨架、74 个测试里的大量参数化边界、FastAPI 样板、文档。这些量大、模式固定、且正确性可以事后独立验证。

自己拍板的：存储与并发方案、金额精度、校验的松紧、关键字段范围、日期解析方式、以及”不做什么”的边界。这些一旦选错，后面全部要返工，而且错了不容易被发现。

人工审查的风险点：

风险 处理
误改原始文件 运行时指纹检查 + 测试守住
写出半截报表 临时文件 + 原子替换
SQL 注入 全部参数绑定，SQL 集中审查
静默篡改金额 明确拒绝 3 位小数 + DB 层兜底
并发”看起来对” 不满足于”能说明即可”，写成测试
测试自我安慰 独立核对脚本 + 变异测试

如果重来，我会先把测试骨架和手算期望值定下来再写实现。这次是边实现边补测试，中间有几处口径（比如日期解析失败算不算缺失）是写测试时才被迫想清楚的，多了一次返工。

写在最后

这次实验让我对”Vibe Coding”有了一个具体的理解。

代码确实大部分是 AI 写的，速度也确实快。但真正决定这份作业质量的，不是生成速度，而是我设计了哪些验证手段：

  • 独立核对脚本，防”自己算自己”
  • 变异测试，防”测试空跑”
  • 真实 HTTP 冒烟，防”TestClient 假绿”
  • 运行时指纹检查，防”误改原始文件”

代码是 AI 写的，但判断它对不对的标准是人定的。 我觉得这就是评分表里说的”过程可控”——不是控制 AI 怎么写，是控制自己怎么验。
